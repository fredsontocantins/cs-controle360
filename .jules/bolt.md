## 2026-07-27 - Smart List Query Reuse vs. Unscaled In-Memory Filtering
**Learning:** In highly relational or list-heavy endpoints like `/api/reports/intelligence`, calling separate model list methods often duplicates full database scans of the same tables under identical conditions (e.g., retrieving lists of activities/releases twice). However, attempting to solve this by fetching the entire historical database tables (`include_history=True`) and filtering them in-memory is a major performance and scaling anti-pattern that increases CPU/memory usage, network latency, and violates module encapsulation boundaries.
**Action:** Always prefer reusing already-fetched, parameter-identical standard model collections within the router/service layer when parameters align (e.g., when `cycle_id is None`). If filtering is required, let the database handle it or perform it via model-level interfaces, rather than exposing internal private filtering functions (like `_within_current_cycle`) to the router layer.
